# MedConnecte : Backend (NestJS 11 + Prisma 7)

API REST + WebSocket de la plateforme de santé. Voir aussi le `CLAUDE.md` racine
(architecture globale + liste complète des problématiques).

## Stack & démarrage

- **NestJS 11**, **Prisma 7** (driver adapter `pg`), **PostgreSQL**, **Socket.io**,
  **BullMQ** (Redis), **JWT** (passport), **bcrypt**, Swagger.
- Lancé via Docker (voir racine). Local : `npm run dev` (= `nest start --watch`).
- Swagger : `/api`. Port : `3001`.

## Structure

`src/<domaine>/` = un module Nest (controller + service + dto + module). Domaines :
`auth`, `user`, `structure`, `super-admin`, `carnet-sante` (cœur métier : profil,
consultations, ordonnances, analyses, vaccinations, RDV, **urgences SOS**),
`pharmacie`, `geo`, `chat` (socket.io), `notifications`.

Services transverses dans `src/common/services/` : `prisma`, `encryption` (AES-256-GCM
des données médicales), `email` (Resend), `sms` (Nimba), `ai`. Le **stockage objets**
vit désormais dans son propre module `src/storage/` (**Cloudflare R2**, cf. plus bas) ;
l'ancien `src/common/storage.*` (S3/MinIO générique) est **dormant, à retirer**.
File asynchrone dans `src/queue/` (**BullMQ**).

## Conventions importantes (pièges)

- **Client Prisma généré** dans `../generated/prisma` (hors `node_modules`, gitignoré).
  - Import en *bare specifier* : `import { … } from 'generated/prisma/client'`.
  - Build : `prisma generate` obligatoire. Runtime prod : démarré avec
    `node -r tsconfig-paths/register dist/src/main.js` pour résoudre ce bare import
    (baseUrl `./`). **Ne pas** retirer le `tsconfig-paths/register`.
  - `prisma.config.ts` lit `DATABASE_URL` ; le `datasource` n'a pas d'`url` (driver adapter).
- **Migrations** appliquées au démarrage du conteneur par `docker-entrypoint.sh`
  (`prisma migrate deploy`). En dev, l'entrypoint **resynchronise aussi** `node_modules`
  (npm ci si `package-lock.json` a changé) et le client Prisma (si `schema.prisma` a
  changé), via comparaison de hash → après un ajout de dépendance, un simple
  `docker compose up`/`restart` suffit (plus besoin de `down -v`).
- **`npm ci` est strict** : garder `package.json` ↔ `package-lock.json` synchro
  (`npm install --package-lock-only` après édition manuelle).
- **Auth** : `AuthGuard` (`src/common/guards/auth.guard.ts`) attend `JwtService` →
  tout module exposant un contrôleur guardé doit `imports: [AuthModule]`.
  `req.user.userId` / `req.user.role` après garde. RBAC via `@Roles(...)` + `RolesGuard`.
- **Permissions selon le type de structure (B10)** : `PermissionsService.getUserPermissions` (seule source des permissions effectives : `PermissionsGuard`, `/auth/me`, diffusion SOS, chat, fichiers) filtre les permissions du rôle selon le type de la structure de l'utilisateur (`structure`, à défaut `administeredStructure`), règle dans `src/common/rbac/permissions-type-structure.ts`. Une PHARMACIE ne garde qu'une liste blanche : `stock:read`, `stock:write`, `catalogue:write`, `catalogue:manage`, `vente:read`, `vente:write`, `vente:annuler`, `caisse:utiliser`, `caisse:superviser`, `cloture:gerer`, `inventaire:write`, `reception:write`, `marge:read`, `anomalie:gerer`, `structure:read`, `structure:write`, `membre:read`, `membre:manage`, `role:manage`, `chat:structure` ; aucun accès au dossier médical (carnet, consultations, ordonnances, analyses, vaccinations, rendez-vous, liste des patients, SOS), même par un rôle personnalisé (le rôle en base n'est pas modifié, la permission y est inopérante). HOPITAL, CLINIQUE et utilisateur sans structure : inchangés, sauf que les permissions de vente et de caisse (les trois `vente:*` et les sept de la tranche pharmacie 1 : `caisse:utiliser`, `caisse:superviser`, `cloture:gerer`, `inventaire:write`, `reception:write`, `marge:read`, `anomalie:gerer`) leur sont retirées (réservées aux pharmacies, même par un rôle personnalisé). Toute nouvelle permission est refusée aux pharmacies tant qu'elle n'est pas ajoutée à la liste blanche. Cache Redis `perms:v3:user:<id>` (5 min). `GET /auth/me` renvoie `data.structureType` (`HOPITAL`, `CLINIQUE`, `PHARMACIE` ou `null`) et `data.permissions` filtrées : le front construit menu et tableau de bord à partir de ces deux champs, pas du rôle enum.
- **Sessions (TB3)** : une connexion = une ligne `Session` (modèle Prisma) = une famille
  de refresh. Le refresh a le format `<sessionId>.<secret>` et seul le sha256 du secret
  est stocké. `SessionsService` (`src/auth/sessions.service.ts`) est le seul endroit qui
  émet, tourne ou révoque un refresh.
  - Web : refresh uniquement dans le cookie httpOnly `refresh_token`, jamais dans le JSON.
    Mobile : en-tête `X-Client: mobile`, `deviceId` et `plateforme` obligatoires à la
    connexion, refresh envoyé et reçu dans le corps (`refreshToken`, `expiresIn`,
    `sessionId`), jamais de cookie.
  - Rotation à chaque refresh, grâce de 30 s (l'ancien refresh renvoie le refresh
    courant). Réutilisation hors grâce : session révoquée et 401 `REFRESH_REUTILISE`.
  - Durées : jeton d'accès 15 min portant `sid` ; sessions glissantes de 30 jours (web,
    mobile patient) et 12 h (mobile autres rôles), Q11 révisable.
  - `POST /auth/logout` est public (refresh seul ou jeton d'accès).
  - Erreurs (TB2) : le corps `{ statusCode, message, error }` peut porter `code` (catalogue `src/common/filters/codes-erreur.ts`, toute 403 sans code reçoit PERMISSION_REFUSEE), `champs` pour VALIDATION (nom et contraintes, jamais la valeur, y compris en production) et `donnees` (liste blanche, aujourd'hui `peutRelancerA` du 409 SOS_DEJA_ACTIF). Le SOS est réservé au rôle PATIENT (403 SOS_ROLE_INTERDIT) ; le patient n'annule un rendez-vous que depuis PROGRAMME, EN_ATTENTE ou CONFIRME (409 TRANSITION_INTERDITE).
  - Révocation (TB4) : routes `GET /auth/sessions`, `DELETE /auth/sessions/:id` et
    `POST /auth/sessions/revoquer-autres`. Le changement de mot de passe déconnecte les
    autres appareils (`deconnecterAutresAppareils`, vrai par défaut) ; la réinitialisation
    et la désactivation du compte révoquent tout. `AuthGuard` contrôle chaque requête par
    `RevocationService` (état en Redis : 30 s si valide, 16 min si révoqué, repli
    PostgreSQL). L'événement socket `sessionRevoquee` `{ code, message }` précède la
    déconnexion. Purge horaire des sessions expirées ou révoquées depuis plus de 30 jours.
- **Limiteur de débit** : `UserThrottlerGuard` (garde globale) compte par utilisateur en lisant le jeton Bearer (signature vérifiée), sinon par IP ; `/auth/register`, `/auth/login`, `/auth/forgot-password` et `/auth/reset-password` restent comptés par IP. Stockage Redis (`StockageLimiteRedis`, script Lua, juste à plusieurs instances). Redis absent ou plus lent que 250 ms : les routes `@LimitePermissiveSiRedisIndisponible()` (le SOS) passent, les autres sont comptées en mémoire locale. L'email et le SMS au proche d'un SOS sont mis en file avec un délai de 2 s, sans faire échouer l'alerte.
- **Version et configuration publiques (TB5)** : module `src/configuration-publique/`. `GET /app/version` (public, `Cache-Control: public, max-age=60`) renvoie `{ success, data: { android, ios } }`, chaque plateforme `{ versionMinimale, versionRecommandee, urlTelechargement }` (URL `null` si non réglée ; recommandée jamais sous la minimale). `GET /app/config` (public, `max-age=300`) renvoie `{ success, data: { numerosUrgence: [{ code, libelle, numero }], versionsDocuments: { cgu, politiqueConfidentialite }, fonctions: { espaceSoignant, annulationSos, boutonDemo } } }`, sans donnée sensible. Les deux routes échappent au limiteur (`@SkipThrottle`). `VersionMinimaleGuard` (garde globale, avant le limiteur) répond 426 `VERSION_OBSOLETE` à un client qui envoie `X-Client: mobile`, `X-Plateforme` (`android` ou `ios`) et une `X-App-Version` inférieure à la minimale de sa plateforme, sur toute route sauf `/app/*` ; un en-tête absent ou illisible laisse passer, le web n'est jamais affecté. Versions lues au format `1`, `1.4` ou `1.4.2` (suffixe `-beta` ignoré). Le numéro d'urgence a une source unique, `src/config/numeros-urgence.ts`, lue aussi par le repli de `AiService`. `X-Api-Version` est réservé (version 1 implicite), non lu.
- **Un numéro par compte (TB17)** : `normaliserTelephone` (`src/common/telephone/telephone.ts`) est la seule règle (préfixe `+224`, `00224`, `224` ou aucun, puis 9 chiffres ; espaces, points et tirets ignorés ; résultat `+224XXXXXXXXX`), reprise à l'identique par la fonction SQL `telephone_e164`. Toute écriture de `User.telephone` passe par `exigerTelephone` (400 `VALIDATION`, champ `telephone`), `verifierTelephoneLibre` et `avecTelephoneUnique` (`src/common/telephone/telephone-unicite.ts`) : 409 `TELEPHONE_DEJA_UTILISE` « Ce numéro est déjà utilisé par un autre compte. », y compris en cas de course (P2002). L'unicité repose sur la colonne dérivée `User.telephoneNormalise`, tenue par un trigger PostgreSQL (ne jamais l'écrire), et sur un index unique partiel (préversion Prisma `partialIndexes`) : un compte sans numéro reste possible, un compte désactivé garde son numéro. Les anciennes valeurs de `telephone` ne sont pas réécrites. Avant de déployer la migration `20261021120000_tb17_telephone_unique`, lister les doublons en lecture seule : `npm run telephones:doublons` (dev) ou `node dist/scripts/telephones-doublons.js` lancé par `docker compose run --rm --entrypoint ""` (production) ; s'il en reste, la migration échoue sans rien appliquer (`prisma migrate resolve --rolled-back` puis nouveau déploiement après décision du porteur).
- **Structure de rattachement d'un utilisateur (U1)** : un compte appartient à un établissement par `User.structureId` (membres et administrateur) ; l'administrateur l'est aussi par `Structure.adminId`. `GET /users` et `GET /users/:userId` renvoient `structure { id, nom, type }` résolue dans cet ordre (`structureId`, sinon structure administrée, sinon `null`) ; `structureId` reste la valeur brute. `UserResponseDto` filtre par `excludeExtraneousValues` : tout champ ajouté à la réponse doit y être exposé (`@Expose`, et `@Type` pour un objet). Contrôle en lecture seule des rattachements incomplets ou incohérents : `npm run structures:rattachements` (dev) ou `node dist/scripts/structures-rattachements.js` lancé par `docker compose run --rm --entrypoint ""` (production) ; aucun correctif automatique.
- **SOS : qualité de la position et idempotence (TB10b)** : `POST /carnet-sante/sos` accepte les champs optionnels `precision` (mètres, 0 ou plus), `horodatagePosition` (ISO 8601) et `source` (`gps`, `reseau`, `inconnue`), enregistrés dans `Urgence` (`precisionMetres`, `horodatagePosition`, `sourcePosition`). Règle de `src/carnet-sante/sos-position.ts` : plus de 15 min ou plus de 2 000 m, la position est enregistrée mais non utilisée (aucune structure prévenue, pas de lien de position au proche, message au patient qui lui demande d'appeler les secours, relance possible aussitôt) ; plus de 500 m, elle est utilisée et signalée par `avertissementPosition` dans la charge `emergencyAlert` et dans la notification aux soignants ; un horodatage en avance de plus de 5 min est ignoré ; sans precision ni horodatage, comportement d'avant. La réponse gagne `positionUtilisee`, `qualitePosition`, `precisionMetres`, `rejeu`, et `diffusionEnCours` pour un rejeu arrivé pendant l'envoi. En-tête facultatif `Idempotency-Key` (8 à 128 caractères `[A-Za-z0-9._:-]`, sinon ignoré) : même patient et même clé dans les 24 h donnent la même alerte, réponse 201 rejouée depuis `Urgence.bilanDiffusion`, sans nouvelle diffusion ni 409. Stockage en base (unicité `patientId` + `cleIdempotence`), indépendant de Redis ; `cleIdempotence` et `bilanDiffusion` ne sortent jamais dans les réponses ; aucune coordonnée dans les journaux.
- **Ventes en pharmacie (B13, lot 7 ; B14, lot 8)** : module `src/pharmacie/` (`VenteController`, `VenteService`, DTO `dto/vente.dto.ts`). Quatre routes sous `/pharmacie`, gardes `AuthGuard` + `PermissionsGuard`, accès contrôlé par `AccesPharmacieService` (`src/pharmacie/acces-pharmacie.service.ts`, commun au stock et aux ventes) : membre de la pharmacie ou son administrateur quel que soit l'enum `role`, structure de type PHARMACIE (403 « Vous n'avez pas accès à cette pharmacie. » sinon) et active (403 « Cette pharmacie est désactivée. Contactez l’administrateur de la plateforme. ») : `POST /pharmacie/:structureId/ventes` (`vente:write`, 201), `GET /pharmacie/:structureId/ventes` (`vente:read`, 200), `GET /pharmacie/:structureId/ventes/:venteId` (`vente:read`, 200, 404 « Cette vente est introuvable. »), `POST /pharmacie/:structureId/ventes/:venteId/annuler` (`vente:annuler`, 200). Toutes les réponses sont `{ data, message, success }`.
  - Contrat actuel : création par PB11 (puce « Vente recâblée »), annulation et liste par PB12 (puce « Annulation par pièce inverse »), journée clôturée par PB17c, rejeu des ventes hors ligne par PB18. Forme de base de la réponse (création, rejeu, détail, annulation) : `{ id, numero, statut, createdAt, total, ordonnanceVerifiee, clientNom, clientTelephone, vendeur: { id, nom }, annuleeLe, annuleeParId, motifAnnulation, lignes, pharmacie: { id, nom, adresse, ville, telephone, logoUrl } }` (les puces PB11 et PB12 ajoutent les clés de la caisse). `data.rejeu: true` n'est présent QUE sur un rejeu d'une même `Idempotency-Key` (absent sinon). `clientNom`, `clientTelephone` et les champs de `pharmacie` absents valent `null` ; `logoUrl` est l'URL publique pérenne du logo (bucket public, `R2_PUBLIC_URL`) ou `null`. Les noms et prix des lignes sont des copies figées au moment de la vente. Corps : `clientNom` de 100 caractères au plus, `clientTelephone` de 30 au plus, 1 à 50 lignes. Les `details` des codes à lignes sont assainis par `AllExceptionsFilter` (`CODES_AVEC_DETAILS`, 50 éléments au plus). Erreurs sans code : 404 « Cette pharmacie est introuvable. » et 404 « Cette vente est introuvable. ». Une vente n'est jamais supprimée, seulement annulée (pièce inverse) ; `vendeurId`, `annuleeParId` et les identifiants des lignes n'ont pas de clé étrangère.
  - Prix du stock désormais entier (GNF, colonne `Int`, migration `20261022120000_ventes_pharmacie` avec arrondi) : `UpsertStockDto.prixUnitaire` en `@IsInt` (0 à 2147483647), import Excel arrondi à l'entier (rejet au-delà de 2147483647) ; `UpdateStockQuantiteDto.variation` en `@IsInt`. Permissions des pharmacies : rôle « Pharmacien » : `stock:read`, `stock:write`, `catalogue:write`, `vente:read`, `vente:write`, `caisse:utiliser`, `reception:write` (D732, migration `20261104100000_pharmacie_t1_pharmacien_reception` pour les rôles existants, jamais rétabli au démarrage s'il est retiré ; le coût saisi sur un bon de livraison n'est pas relu sans `marge:read` ; `inventaire:write` reste au titulaire, D598), `chat:structure`, `structure:read`, `membre:read` ; rôle « Administrateur de structure » : les 12 permissions de `PERMISSIONS_GARANTIES_ADMIN_PHARMACIE` (`stock:read`, `stock:write`, `vente:read`, `vente:write`, `vente:annuler` et les sept de la tranche pharmacie 1), plus `structure:read`, `structure:write`, `membre:read`, `membre:manage`, `role:manage`. Rôles existants : `vente:*` repris par la migration du lot 7 ; depuis B14, `RolesService.completerRolesAdminPharmacie` ajoute au démarrage les 12 permissions de `PERMISSIONS_GARANTIES_ADMIN_PHARMACIE` au rôle « Administrateur de structure » de chaque pharmacie (ajout seul, invalidation du cache du rôle ; une de ces permissions retirée à la main revient au démarrage suivant). Hôpitaux et cliniques : ni `stock:*` ni `vente:*` (voir B10), cache `perms:v3`.
- **Imports Excel de la pharmacie (stock et catalogue)** : `src/pharmacie/import-excel.ts`. La ligne des titres est la première des 10 premières lignes qui contient toutes les colonnes obligatoires (stock : Médicament, Quantité ; catalogue : Nom, Catégorie), sinon 400 qui nomme les colonnes manquantes. Titres comparés en minuscules sans accents ni ponctuation (`normaliserTitre`), synonymes dans `reconnaitre` de `COLONNES_IMPORT_STOCK` (`pharmacie.service.ts`) et `COLONNES_IMPORT_CATALOGUE` (`catalogue-import.service.ts`) : Désignation, Produit, Libellé, Qté, P.U., Péremption, DCI, Famille… ; un titre de seuil (« Quantité minimale », « Stock alerte ») n'est jamais pris pour la quantité. - **Points de vente, postes et référentiels (tranche pharmacie 1, PB05)** : migration `20261026100000_pharmacie_t1_points_de_vente` (M2, retour arrière dans `prisma/retours-arriere/`) : tables `PointDeVente` (un par pharmacie, `ordre` 1), `Poste` (dont le poste technique `REPRISE`, inactif, jamais exposé), `CompteurTicket`, `PlageTicket`, `ParametresPharmacie`, `ModePaiement` (`ESPECES`, `ORANGE_MONEY`, `MTN_MOMO` ; un nouveau mode = un `INSERT`), `CoupureMonnaie` (billets de 20 000, 10 000, 5 000, 2 000, 1 000 et 500 GNF), `Fournisseur`, `Anomalie`, clés étrangères en `Restrict`. La migration s'arrête et liste les structures qui ne sont pas des pharmacies et portent du stock ou des ventes. `assurerPointDeVente` (`src/pharmacie/point-de-vente.ts`, idempotent) crée point de vente, poste `REPRISE`, compteur et paramètres : à la création d'une pharmacie par le super administrateur (non bloquant), dans le jeu démo, au démarrage (`PointsDeVenteService.completerPointsDeVente`, pharmacies sans point de vente ou sans paramètres) et au premier accès ; `supprimerConfigurationPharmacies` retire cette configuration avant toute suppression de structure (super administrateur, purge démo). Garde de dérive : `test/db/schema-derive.db-spec.ts` exige que `prisma/schema.prisma` corresponde exactement à la base migrée (`prisma migrate diff --exit-code`).
- **Fiche produit étendue (tranche pharmacie 1, PB06)** : migration `20261026110000_pharmacie_t1_fiche_produit` (M3, retour arrière dans `prisma/retours-arriere/`) : `StockMedicament` gagne `uniteMinimale` (enum `UniteMinimale` : `COMPRIME`, `GELULE`, `ML`, `SACHET`, `GRAMME`, `AMPOULE`, `PLAQUETTE`, `UNITE`, défaut `UNITE` ; `PLAQUETTE` ajoutée par la migration additive `20261103100000_pharmacie_t1_unite_plaquette` (PB21, D723, retour arrière refusé tant qu'une fiche l'utilise) : coefficient = plaquettes par boîte, `prixUnite` = prix de la plaquette ; changer l'unité d'une fiche qui a du stock donne 409 `UNITE_CHANGEMENT_AVEC_STOCK` (D724), sauf pour une fiche non qualifiée en `UNITE` à coefficient 1 : qualification de la reprise avec coefficient conservé, ou conversion PB13 avec `conversionStock` ; une fiche qualifiée, ou non qualifiée dont l'unité n'est pas `UNITE` ou dont le coefficient n'est pas 1, reste refusée), `coefficientBoite` (unités par boîte, défaut 1, au moins 1), `prixUnite` (prix d'une unité, nul ou positif, permis seulement si `deconditionnable`), `deconditionnable` (défaut faux), `toleranceInventaire` (unités, nul ou positif), `qualifie` (défaut faux), `archiveLe` et `createdAt` ; `prixUnitaire` garde son nom et vaut le prix de la boîte. Les lectures de stock renvoient ces colonnes.
- **Journal de stock (tranche pharmacie 1, PB07)** : migration `20261026120000_pharmacie_t1_lots_mouvements` (M4, retour arrière dans `prisma/retours-arriere/`, qui restaure `quantite` depuis la somme des mouvements écrêtée à 0 et liste les fiches écrêtées). Tables `LotStock` (lot par fiche et point de vente, figé après insertion sauf `dateExpiration`, et `coefficientReception`/`coutUnitaire` d'un lot technique), `MouvementStock` (journal append-only : jamais modifié ni supprimé, trigger `journal_refuser_modification`, quantités signées en unités minimales, `evenementId` unique), `AgregatStockLot` (solde par lot, jamais négatif) et `AgregatStockProduit` (solde par fiche et point de vente, peut être négatif), agrégats de lecture tenus uniquement par le trigger `mouvement_stock_agreger` (ne jamais les écrire), `ConditionnementOuvert` (au plus un ouvert par fiche, lot et point de vente, index unique partiel). La reprise a créé un lot technique (coût 0, date de la fiche) et un mouvement `RECEPTION` pièce `MIGRATION` (`evenementId` `migration:<stockId>`) par fiche à quantité positive. `StockMedicament.quantite` et `disponible` sont gelées (trigger `stock_medicament_geler_compteur` : une fiche se crée à quantité nulle, toute modification de ces deux colonnes est refusée) ; elles seront supprimées à la version suivante. Postes attendus (D616) : caisse encore ouverte sur le jour, poste desktop à file non vide, poste desktop qui a vendu dans les 7 jours sans synchro complète depuis le début du jour ; 409 `CLOTURE_INCOMPLETE` (postes dans `details`). Forcer exige un motif (400 `MOTIF_REQUIS`) et n'est permis que si tous les postes attendus sont desktop : une caisse ouverte sur un navigateur se ferme avec le comptage (409 `CAISSES_A_FERMER`). La clôture passe les caisses fermées du jour en `INCLUSE_DANS_CLOTURE`, fige `TotalClotureMode` (compté nul si une caisse n'a pas de relevé pour un mode qu'elle a encaissé) et consigne les postes manquants (`posteId`, `posteCode`, `libelle`, `type`, `raison`, `sessionId`, `utilisateurNom`, `dernierContactLe`) ; une caisse desktop ouverte reste ouverte. 409 `JOURNEE_DEJA_CLOTUREE`. Verrou consultatif de journée `medconnecte:journees:<structureId>` pris en exclusif en tête de la clôture (`src/pharmacie/caisse/journee.ts`, D613). Export : `GET .../caisse/clotures/:jour/export` (`cloture:gerer`, journée clôturée seulement, sinon 409 `JOURNEE_NON_CLOTUREE`) renvoie un CSV `cloture-AAAA-MM-JJ.csv` (point-virgule, UTF-8 avec BOM) : une ligne par pièce (vente, annulation, régularisation), par paiement (montant signé, référence) et par mouvement de caisse (apport positif, prélèvement et remboursement négatifs), colonne « Caisse incluse dans la clôture », sans coût, sans client, sans médicament ; formules Excel neutralisées, référence de paiement faite uniquement de chiffres précédée d'une apostrophe (D622, D628).
- **Journée clôturée (tranche pharmacie 1, PB17c)** : vente, annulation, ouverture de caisse, comptage, mouvement de caisse et fermeture prennent en tête de transaction le verrou de journée partagé (`verrouillerJourneesPartage`), la clôture le prend en exclusif : aucune écriture ne s'intercale. Ordre des verrous : journées, poste, session, compteur de tickets ou vente d'origine, fiches. Une caisse dont le jour métier est clôturé (caisse desktop restée ouverte après une clôture forcée) refuse toute écriture : 409 `JOURNEE_CLOTUREE`. Une caisse ouverte après la clôture du jour compte pour le lendemain (`jourMetierOrigine` = jour réel) : aucune vente n'est refusée pour ce motif. Une correction se fait par écriture inverse rattachée à la journée en cours qui pointe l'origine (annulation, CA20). Une réception datée d'un jour antérieur clôturé est refusée ; le journal de stock (inventaire, sortie, corrections, résolution des provisoires) est horodaté au présent et n'est jamais refusé (D614). Tout nouvel écrivain de caisse (rejeu PB18 compris) s'ajoute au test 11 de `test/db/journee-cloturee.db-spec.ts`, qui exige qu'il attende une clôture en cours avant sa première lecture (D629).
- **Synchronisation desktop (tranche pharmacie 1, PB18)** : `POST /pharmacie/:structureId/postes/:posteId/plages` (`caisse:utiliser`, 200, `{ id }` UUID du poste) réserve `taillePlageTickets` numéros sur `CompteurTicket` pour un poste DESKTOP actif (idempotent par `id`, 409 `IDENTIFIANT_DEJA_UTILISE` pour l'id d'un autre poste, 409 `PLAGES_SUFFISANTES` au-delà de deux plages non épuisées, 409 `POSTE_INCONNU` pour un poste web, technique, inactif ou inconnu) ; une plage est épuisée quand son dernier numéro ou un numéro d'une plage plus récente du poste est utilisé ; la réponse liste les plages en cours. `GET /pharmacie/:structureId/synchro/catalogue?posteId=` (`caisse:utiliser`) renvoie la photographie complète du catalogue pour un poste desktop actif (fiches non archivées, lots à solde positif périmés compris, paramètres, modes, coupures, pharmacie, plages en cours, `sequenceAppliquee` et `sequenceMaxRecue` ; par fiche, `quantite` écrêtée à 0 et `quantiteARegulariser`, jamais le négatif, D719), sans aucun coût même pour le titulaire, lue en lecture répétable, avec ETag faible (304 si `If-None-Match` correspond) et compression brotli ou gzip selon `Accept-Encoding` (D633, D634) ; aucun champ qui dépend de l'heure dans la photographie, le poste lit l'heure du serveur dans l'en-tête `Date` (D662). CORS : `DESKTOP_ORIGINS` (D635), en-têtes exposés `ETag` et `Date`. `POST /pharmacie/:structureId/synchro/evenements` (`caisse:utiliser`, 200, corps JSON jusqu'à 2 Mo, gzip accepté ; seule route ainsi : partout ailleurs 100 Ko et 415 sur un corps compressé, `monterAnalyseursJson` de `src/config/analyseurs-corps.ts`, à monter avant `init`, D663) : `{ posteId, etat: { fileVide, sessionOuverte, versionApp }, evenements: [{ evenementId, sequence, type, horodatageLocal, utilisateurId, corps }] }` (0 à 200 ; lot vide = battement de cœur). Une transaction par événement, verrou de journée partagé en tête puis poste ; idempotent par `evenementId` et empreinte ; ordre strict par poste (`EN_ATTENTE` puis application dès que le trou est comblé, saut après 24 h avec `SEQUENCE_MANQUANTE`) ; statuts `APPLIQUE`, `DEJA_APPLIQUE`, `EN_ATTENTE`, `REJETE` (stocké avec son corps, séquence avancée, anomalie `EVENEMENT_REJETE` sans donnée du client), `A_RENVOYER` (rien d'écrit, renvoyer plus tard ; au 3e échec imprévu du même événement, hors panne passagère de la base, il est mis de côté `REJETE` `EVENEMENT_INAPPLICABLE`, compteur dans `Poste.dernierEtat.echecImprevu` ; un caractère NUL donne `EVENEMENT_INVALIDE` et le corps est stocké en texte `{ corpsIllisible }`, D664) ; réponse `{ resultats, sequenceAppliquee, enAttente }`, avec les événements en attente traités pendant l'appel (`differe`). Le vendeur d'un événement doit être de la pharmacie (`UTILISATEUR_NON_AUTORISE`). Écrit `Poste.dernierContactLe` et `dernierEtat` (`fileVide` = déclaré et rien en attente). Événements de caisse : `SESSION_OUVERTE` (jour local, ou jour de rattachement si clôturé), `COMPTAGE_SAISI`, `MOUVEMENT_CAISSE` (appliqués sur une caisse ouverte même d'un jour clôturé), `SESSION_FERMEE` (jamais refusée ; caisse d'un jour clôturé : FERMEE, jamais incluse, anomalie `REMONTEE_APRES_CLOTURE` au titulaire). Le cœur de fermeture est `SessionsCaisseService.fermerSessionVerrouillee` (D650). Le rejeu figure au test 11 de `journee-cloturee.db-spec.ts`. Événement `VENTE` `{ venteId, sessionId, numeroTicket ou numeroSecours, lignes [{ stockId, unite, nombre, prixUnitaire, quantiteProvisoireLocale?, ouvertureConditionnement?, sortieManuelle? }], paiements, total, clientNom?, clientTelephone?, ordonnanceVerifiee }` : le serveur réalloue les lots au jour local de la vente (prix du ticket gardé, coefficient actuel pour une boîte, jamais de lot périmé pris automatiquement, reste provisoire avec `STOCK_NEGATIF`, aussi quand la ligne était provisoire sur le poste) ; anomalies `PRIX_DIVERGENT` (jamais en plus de `VENTE_UNITE_INTERDITE` pour une même ligne, D666), `VENTE_UNITE_INTERDITE`, `ORDONNANCE_NON_CONFIRMEE`, `PRODUIT_ARCHIVE`, `CONDITIONNEMENT_CONCURRENT`, `PLAGE_EPUISEE` au titulaire, jamais de refus de fond ; numéro de plage `T<ordre>-NNNNNNN`, de secours `S<ordre>-<poste>-<n>`, hors plage `N<ordre>-<poste>-<séquence>` ; `Vente.id` = `venteId`, mouvements `synchro:<evenementId>:<ligne>:<lot ou provisoire>` (aucun double rejeu possible) ; incohérence interne (total, paiements, numéros) : `EVENEMENT_INVALIDE` ; fiche inconnue : `STOCK_INTROUVABLE` ; vente remontée sur une caisse d'un jour clôturé ou déjà fermée : pièce `REGULARISATION` sur la caisse d'origine (paiements compris), `jourMetier` = journée en cours (jour de rattachement), `jourMetierOrigine` = jour de la caisse, anomalie `REMONTEE_APRES_CLOTURE` nominative au vendeur de la caisse (raison `JOURNEE_CLOTUREE` ou `CAISSE_FERMEE`, clôture retrouvée par le jour, `posteManquantDeLaCloture`) ; la journée clôturée (pièces, caisses incluses, totaux, export) ne change jamais ; l'export de la journée en cours montre la régularisation avec une caisse non incluse ; une régularisation n'est pas annulable (D659). L'écriture d'une pièce est partagée avec la vente web (`ecrirePieceVente`, D657) ; le rejeu passe `provisoireAutorise: true` et reste inchangé (D713.2 : la vente faite hors ligne est toujours acceptée, provisoire si besoin, avec anomalie `STOCK_NEGATIF`), alors que la vente web passe `false` (D716, filet `RangeError`). Journal et agrégat peuvent rester négatifs, jamais une sortie d'API : la photographie du poste est écrêtée comme les autres lectures.
- **Exploitation de la tranche pharmacie 1 (PB19)** : pour un développeur ou un exploitant (D679, D680).
  - Contrôle du stock : après une restauration, une intervention en base ou un incident, lancer `stock:verifier` (dev `docker compose exec -T backend npm run stock:verifier`, production `node dist/scripts/stock-verifier.js` par `docker compose run --rm --entrypoint ""`). Agrégats ou conditionnements faux : `stock:reconstruire`. Lots négatifs, plages superposées ou allocations incohérentes : analyse requise, jamais de correction SQL des tables immuables.
  - Événement mis de côté (`REJETE` avec le code `EVENEMENT_INAPPLICABLE`, D664) : (a) le repérer par l'anomalie `EVENEMENT_REJETE` du titulaire (`details.evenementId`) ; (b) lire son corps en lecture seule, depuis la racine : `docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'` avec, sur l'entrée standard, `SELECT "evenementId", "sequence", "type", "horodatageLocal", "corps", "resultat" FROM "EvenementSynchro" WHERE "statut" = 'REJETE' AND "resultat"->>'code' = 'EVENEMENT_INAPPLICABLE' ORDER BY "recuLe";` ; (c) corriger la cause côté serveur et déployer ; (d) aucun rejeu n'existe en T1 : ne jamais modifier, supprimer ni réinsérer la ligne (immuabilité, séquence du poste déjà avancée). Reporter l'effet à la main : une `VENTE` est ressaisie par le titulaire sur sa caisse web (mêmes médicaments, prix et paiements) quand l'argent du tiroir du poste lui est remis, puis l'anomalie est traitée en citant le numéro du ticket d'origine ; tout autre type : traiter l'anomalie avec un commentaire qui décrit la correction faite. Un outil de rejeu reste à décider (porteur).
  - Argent d'une régularisation hors clôture (D659, D667) : une vente remontée après une clôture forcée reste sur la caisse d'origine, jamais incluse : son argent n'entre dans aucun `TotalClotureMode`. Le titulaire le voit par l'anomalie `REMONTEE_APRES_CLOTURE` (raison `JOURNEE_CLOTUREE` au vendeur, raison `CAISSE_FERMEE_APRES_CLOTURE` à lui-même avec `montantEncaisse`), par l'export du jour de rattachement (« Non » dans « Caisse incluse dans la clôture ») et par le bilan de la caisse d'origine. Procédure : recompter le tiroir, traiter l'anomalie avec le montant constaté ; ne saisir ni apport ni vente de plus (la vente est déjà enregistrée). Un rapprochement explicite reste à concevoir (porteur).
  - Paiement arrivé après la fermeture d'une caisse du jour (raison `CAISSE_FERMEE`, `jourMetier` égal à `jourMetierOrigine`) : la caisse est incluse dans la clôture du jour mais son bilan figé (`ResultatSessionMode`) ne compte pas ce paiement ; les totaux de clôture le sous-estiment d'autant. Le titulaire l'ajoute à la main d'après l'anomalie ; le front (PF05, PF06) affiche l'anomalie à côté de la clôture. Changement du calcul : décision du porteur.

## Mode démo (`src/demo/`)

Actif seulement si `DEMO_MODE=true` (avertissement au démarrage, renforcé en production).
`DemoSeeder` joue le jeu en deux phases, une seule fois au boot :
- **Phase 1**, en une transaction : structures, comptes, carnets chiffrés via
  `EncryptionService`, messagerie, SOS, notifications, points de vente des pharmacies,
  `debutCaisse` et `debutFiabiliteMarge` reculés de 30 jours, 16 fiches de stock qualifiées, avec
  un prix de boîte et, pour les déconditionnables, un prix à l'unité (sauf Spasfon à la
  Pharmacie du Niger, non qualifié) ; aucun lot ni mouvement,
  puis rattachement des rôles RBAC.
- **Phase 2**, jouée par les services de la pharmacie (`ScenarioDemoPharmacieService`,
  `src/pharmacie/demo/`) seulement juste après une création ou une remise à zéro, une
  transaction par opération, jamais d'écriture directe d'une pièce (sauf le lot technique
  du Spasfon). Pharmacie de Kaloum : réceptions avec lots (péremptions à 7, 30 et 90 jours,
  un lot sans coût), inventaire avec écart et lot périmé trouvé, poste desktop « Comptoir
  principal » avec plage de tickets, journée J-2 clôturée et exportable, journée J-1
  clôturée de force avec une vente remontée en régularisation, caisses web ouvertes du
  jour, boîte entamée, annulation, anomalies. La vente de Ventoline sans stock est remontée
  par le poste (lot C : caisse S3 du jour ouverte à 00:10, comptée, ticket 10, restée
  ouverte), seul chemin qui l'accepte (D713, D721) : stock final -1 en base, affiché 0 avec
  une boîte à régulariser ; la route web la refuserait en 409 `STOCK_INSUFFISANT`. Pharmacie du Niger :
  réception, fiche Spasfon reprise à qualifier, ruptures et stock bas. Un échec est
  journalisé `demo.scenario_pharmacie_echoue` (la phase 2 n'est pas atomique, un jeu
  partiel peut subsister) ; remède : `DEMO_RESET=true`. Si les rôles ne se rattachent pas
  après la création, elle est sautée (`demo.scenario_pharmacie_saute`).

Le compte vitrine
patient (Aminata Diallo) porte un dossier riche sur 3 ans (9 consultations dans 3
structures, ordonnances sans pénicilline car elle y est allergique, analyses, vaccins,
rendez-vous, messagerie). Comme le seed ne crée rien si des données démo existent déjà,
`DEMO_RESET=true` (avec `DEMO_MODE=true`) supprime au démarrage toutes les données démo
puis recrée le jeu complet (phase 1 en une seule transaction, purge comprise, puis phase 2).
La purge supprime, dans l'ordre : les comptes en `@demo.medconnecte.gn` et leurs audits,
`purgerPiecesPharmacies`, `purgerStockPharmacies`, `supprimerConfigurationPharmacies`, puis
les structures, le reste partant par cascade ; elle est prouvée sur les 28 tables de la
tranche par `test/db/demo.db-spec.ts`. Le catalogue de médicaments, partagé, n'est jamais
supprimé. `npm run seed:medicaments` ajoute au catalogue global les médicaments manquants,
sans jamais créer de stock ni modifier l'existant. Purge physique volontaire
(pas de soft-delete sur ces données fictives), journalisée « Données de démonstration
supprimées puis recréées ». À remettre à `false` ensuite, sinon chaque redémarrage
recrée les données (nouveaux identifiants, sessions démo invalidées). Procédure pour obtenir
le jeu à jour sur une base de dev (le seeder ne recrée rien si des données démo existent) :
1. dans le `.env` de la racine, `DEMO_MODE=true` et `DEMO_RESET=true` ; 2. recréer le conteneur
(`docker compose up -d backend`, un simple `restart` ne relit pas le `.env`) ; 3. lire
`docker compose logs --tail 50 backend` : « Données de démonstration supprimées puis
recréées » puis « Scénario pharmacie de démonstration joué » (en cas de
`demo.scenario_pharmacie_echoue` ou `demo.scenario_pharmacie_saute`, refaire l'étape 2) ;
4. remettre `DEMO_RESET=false` puis `docker compose up -d backend`. Les dates du scénario sont
relatives au jour de la remise à zéro (J) : une remise à zéro un autre jour décale tout le jeu.
`DEMO_RESET=true`
sans mode démo : avertissement, rien n'est supprimé. Un compte démo
se reconnaît à son email en `@demo.medconnecte.gn` ; son mot de passe est aléatoire et
inconnu, et son mot de passe comme son email ne peuvent pas être modifiés. Aucun email ni SMS réel ne part depuis ou vers un compte démo : `EmailService` ignore toute adresse en `@demo.medconnecte.gn`, le SOS d'un patient démo ne prévient pas son proche (le patient en est informé), et l'OTP de partage d'un patient démo n'envoie pas de SMS mais renvoie le code à l'accueil (`codeDemo`, seulement si le mode démo est actif). Routes
publiques : `GET /auth/demo/comptes` et `POST /auth/demo/connexion` (`{ userId }`, même
réponse et même cookie que `POST /auth/login`, 403 pour tout compte non démo). `GET /auth/demo/comptes`
propose un compte par rôle, et deux administrateurs de structure (Hôpital National Donka,
Pharmacie de Kaloum : stock, ventes et annulation). Mode
inactif : 404 sur ces deux routes et aucune donnée créée. Ne jamais activer sur une
instance qui contient de vraies données de santé.
