# MedConnecte : Backend (NestJS 11 + Prisma 7)

API REST + WebSocket de la plateforme de santé. Voir aussi le `CLAUDE.md` racine
(architecture globale + liste complète des problématiques).

## Stack & démarrage

- **NestJS 11**, **Prisma 7** (driver adapter `pg`), **PostgreSQL**, **Socket.io**,
  **BullMQ** (Redis), **JWT** (passport), **bcrypt**, Swagger.
- Lancé via Docker (voir racine). Local : `npm run dev` (= `nest start --watch`).
- Swagger : `/api`. Port : `3001`.

## Structure

`src/<domaine>/` = un module Nest (controller + service + dto + module). Domaines :
`auth`, `user`, `structure`, `super-admin`, `carnet-sante` (cœur métier : profil,
consultations, ordonnances, analyses, vaccinations, RDV, **urgences SOS**),
`pharmacie`, `geo`, `chat` (socket.io), `notifications`.

Services transverses dans `src/common/services/` : `prisma`, `encryption` (AES-256-GCM
des données médicales), `email` (Resend), `sms` (Nimba), `ai`. Le **stockage objets**
vit désormais dans son propre module `src/storage/` (**Cloudflare R2**, cf. plus bas) ;
l'ancien `src/common/storage.*` (S3/MinIO générique) est **dormant, à retirer**.
File asynchrone dans `src/queue/` (**BullMQ**).

## Conventions importantes (pièges)

- **Client Prisma généré** dans `../generated/prisma` (hors `node_modules`, gitignoré).
  - Import en *bare specifier* : `import { … } from 'generated/prisma/client'`.
  - Build : `prisma generate` obligatoire. Runtime prod : démarré avec
    `node -r tsconfig-paths/register dist/src/main.js` pour résoudre ce bare import
    (baseUrl `./`). **Ne pas** retirer le `tsconfig-paths/register`.
  - `prisma.config.ts` lit `DATABASE_URL` ; le `datasource` n'a pas d'`url` (driver adapter).
- **Migrations** appliquées au démarrage du conteneur par `docker-entrypoint.sh`
  (`prisma migrate deploy`). En dev, l'entrypoint **resynchronise aussi** `node_modules`
  (npm ci si `package-lock.json` a changé) et le client Prisma (si `schema.prisma` a
  changé), via comparaison de hash → après un ajout de dépendance, un simple
  `docker compose up`/`restart` suffit (plus besoin de `down -v`).
- **`npm ci` est strict** : garder `package.json` ↔ `package-lock.json` synchro
  (`npm install --package-lock-only` après édition manuelle).
- **Auth** : `AuthGuard` (`src/common/guards/auth.guard.ts`) attend `JwtService` →
  tout module exposant un contrôleur guardé doit `imports: [AuthModule]`.
  `req.user.userId` / `req.user.role` après garde. RBAC via `@Roles(...)` + `RolesGuard`.
- **Permissions selon le type de structure (B10)** : `PermissionsService.getUserPermissions` (seule source des permissions effectives : `PermissionsGuard`, `/auth/me`, diffusion SOS, chat, fichiers) filtre les permissions du rôle selon le type de la structure de l'utilisateur (`structure`, à défaut `administeredStructure`), règle dans `src/common/rbac/permissions-type-structure.ts`. Une PHARMACIE ne garde qu'une liste blanche : `stock:read`, `stock:write`, `catalogue:write`, `catalogue:manage`, `vente:read`, `vente:write`, `vente:annuler`, `caisse:utiliser`, `caisse:superviser`, `cloture:gerer`, `inventaire:write`, `reception:write`, `marge:read`, `anomalie:gerer`, `structure:read`, `structure:write`, `membre:read`, `membre:manage`, `role:manage`, `chat:structure` ; aucun accès au dossier médical (carnet, consultations, ordonnances, analyses, vaccinations, rendez-vous, liste des patients, SOS), même par un rôle personnalisé (le rôle en base n'est pas modifié, la permission y est inopérante). HOPITAL, CLINIQUE et utilisateur sans structure : inchangés, sauf que les permissions de vente et de caisse (les trois `vente:*` et les sept de la tranche pharmacie 1 : `caisse:utiliser`, `caisse:superviser`, `cloture:gerer`, `inventaire:write`, `reception:write`, `marge:read`, `anomalie:gerer`) leur sont retirées (réservées aux pharmacies, même par un rôle personnalisé). Toute nouvelle permission est refusée aux pharmacies tant qu'elle n'est pas ajoutée à la liste blanche. Cache Redis `perms:v3:user:<id>` (5 min). `GET /auth/me` renvoie `data.structureType` (`HOPITAL`, `CLINIQUE`, `PHARMACIE` ou `null`) et `data.permissions` filtrées : le front construit menu et tableau de bord à partir de ces deux champs, pas du rôle enum.
- **Sessions (TB3)** : une connexion = une ligne `Session` (modèle Prisma) = une famille
  de refresh. Le refresh a le format `<sessionId>.<secret>` et seul le sha256 du secret
  est stocké. `SessionsService` (`src/auth/sessions.service.ts`) est le seul endroit qui
  émet, tourne ou révoque un refresh.
  - Web : refresh uniquement dans le cookie httpOnly `refresh_token`, jamais dans le JSON.
    Mobile : en-tête `X-Client: mobile`, `deviceId` et `plateforme` obligatoires à la
    connexion, refresh envoyé et reçu dans le corps (`refreshToken`, `expiresIn`,
    `sessionId`), jamais de cookie.
  - Rotation à chaque refresh, grâce de 30 s (l'ancien refresh renvoie le refresh
    courant). Réutilisation hors grâce : session révoquée et 401 `REFRESH_REUTILISE`.
  - Durées : jeton d'accès 15 min portant `sid` ; sessions glissantes de 30 jours (web,
    mobile patient) et 12 h (mobile autres rôles), Q11 révisable.
  - `POST /auth/logout` est public (refresh seul ou jeton d'accès).
  - Erreurs (TB2) : le corps `{ statusCode, message, error }` peut porter `code` (catalogue `src/common/filters/codes-erreur.ts`, toute 403 sans code reçoit PERMISSION_REFUSEE), `champs` pour VALIDATION (nom et contraintes, jamais la valeur, y compris en production) et `donnees` (liste blanche, aujourd'hui `peutRelancerA` du 409 SOS_DEJA_ACTIF). Le SOS est réservé au rôle PATIENT (403 SOS_ROLE_INTERDIT) ; le patient n'annule un rendez-vous que depuis PROGRAMME, EN_ATTENTE ou CONFIRME (409 TRANSITION_INTERDITE).
  - Révocation (TB4) : routes `GET /auth/sessions`, `DELETE /auth/sessions/:id` et
    `POST /auth/sessions/revoquer-autres`. Le changement de mot de passe déconnecte les
    autres appareils (`deconnecterAutresAppareils`, vrai par défaut) ; la réinitialisation
    et la désactivation du compte révoquent tout. `AuthGuard` contrôle chaque requête par
    `RevocationService` (état en Redis : 30 s si valide, 16 min si révoqué, repli
    PostgreSQL). L'événement socket `sessionRevoquee` `{ code, message }` précède la
    déconnexion. Purge horaire des sessions expirées ou révoquées depuis plus de 30 jours.
- **Limiteur de débit** : `UserThrottlerGuard` (garde globale) compte par utilisateur en lisant le jeton Bearer (signature vérifiée), sinon par IP ; `/auth/register`, `/auth/login`, `/auth/forgot-password` et `/auth/reset-password` restent comptés par IP. Stockage Redis (`StockageLimiteRedis`, script Lua, juste à plusieurs instances). Redis absent ou plus lent que 250 ms : les routes `@LimitePermissiveSiRedisIndisponible()` (le SOS) passent, les autres sont comptées en mémoire locale. L'email et le SMS au proche d'un SOS sont mis en file avec un délai de 2 s, sans faire échouer l'alerte.
- **Version et configuration publiques (TB5)** : module `src/configuration-publique/`. `GET /app/version` (public, `Cache-Control: public, max-age=60`) renvoie `{ success, data: { android, ios } }`, chaque plateforme `{ versionMinimale, versionRecommandee, urlTelechargement }` (URL `null` si non réglée ; recommandée jamais sous la minimale). `GET /app/config` (public, `max-age=300`) renvoie `{ success, data: { numerosUrgence: [{ code, libelle, numero }], versionsDocuments: { cgu, politiqueConfidentialite }, fonctions: { espaceSoignant, annulationSos, boutonDemo } } }`, sans donnée sensible. Les deux routes échappent au limiteur (`@SkipThrottle`). `VersionMinimaleGuard` (garde globale, avant le limiteur) répond 426 `VERSION_OBSOLETE` à un client qui envoie `X-Client: mobile`, `X-Plateforme` (`android` ou `ios`) et une `X-App-Version` inférieure à la minimale de sa plateforme, sur toute route sauf `/app/*` ; un en-tête absent ou illisible laisse passer, le web n'est jamais affecté. Versions lues au format `1`, `1.4` ou `1.4.2` (suffixe `-beta` ignoré). Le numéro d'urgence a une source unique, `src/config/numeros-urgence.ts`, lue aussi par le repli de `AiService`. `X-Api-Version` est réservé (version 1 implicite), non lu.
- **Un numéro par compte (TB17)** : `normaliserTelephone` (`src/common/telephone/telephone.ts`) est la seule règle (préfixe `+224`, `00224`, `224` ou aucun, puis 9 chiffres ; espaces, points et tirets ignorés ; résultat `+224XXXXXXXXX`), reprise à l'identique par la fonction SQL `telephone_e164`. Toute écriture de `User.telephone` passe par `exigerTelephone` (400 `VALIDATION`, champ `telephone`), `verifierTelephoneLibre` et `avecTelephoneUnique` (`src/common/telephone/telephone-unicite.ts`) : 409 `TELEPHONE_DEJA_UTILISE` « Ce numéro est déjà utilisé par un autre compte. », y compris en cas de course (P2002). L'unicité repose sur la colonne dérivée `User.telephoneNormalise`, tenue par un trigger PostgreSQL (ne jamais l'écrire), et sur un index unique partiel (préversion Prisma `partialIndexes`) : un compte sans numéro reste possible, un compte désactivé garde son numéro. Les anciennes valeurs de `telephone` ne sont pas réécrites. Avant de déployer la migration `20261021120000_tb17_telephone_unique`, lister les doublons en lecture seule : `npm run telephones:doublons` (dev) ou `node dist/scripts/telephones-doublons.js` lancé par `docker compose run --rm --entrypoint ""` (production) ; s'il en reste, la migration échoue sans rien appliquer (`prisma migrate resolve --rolled-back` puis nouveau déploiement après décision du porteur).
- **Structure de rattachement d'un utilisateur (U1)** : un compte appartient à un établissement par `User.structureId` (membres et administrateur) ; l'administrateur l'est aussi par `Structure.adminId`. `GET /users` et `GET /users/:userId` renvoient `structure { id, nom, type }` résolue dans cet ordre (`structureId`, sinon structure administrée, sinon `null`) ; `structureId` reste la valeur brute. `UserResponseDto` filtre par `excludeExtraneousValues` : tout champ ajouté à la réponse doit y être exposé (`@Expose`, et `@Type` pour un objet). Contrôle en lecture seule des rattachements incomplets ou incohérents : `npm run structures:rattachements` (dev) ou `node dist/scripts/structures-rattachements.js` lancé par `docker compose run --rm --entrypoint ""` (production) ; aucun correctif automatique.
- **SOS : qualité de la position et idempotence (TB10b)** : `POST /carnet-sante/sos` accepte les champs optionnels `precision` (mètres, 0 ou plus), `horodatagePosition` (ISO 8601) et `source` (`gps`, `reseau`, `inconnue`), enregistrés dans `Urgence` (`precisionMetres`, `horodatagePosition`, `sourcePosition`). Règle de `src/carnet-sante/sos-position.ts` : plus de 15 min ou plus de 2 000 m, la position est enregistrée mais non utilisée (aucune structure prévenue, pas de lien de position au proche, message au patient qui lui demande d'appeler les secours, relance possible aussitôt) ; plus de 500 m, elle est utilisée et signalée par `avertissementPosition` dans la charge `emergencyAlert` et dans la notification aux soignants ; un horodatage en avance de plus de 5 min est ignoré ; sans precision ni horodatage, comportement d'avant. La réponse gagne `positionUtilisee`, `qualitePosition`, `precisionMetres`, `rejeu`, et `diffusionEnCours` pour un rejeu arrivé pendant l'envoi. En-tête facultatif `Idempotency-Key` (8 à 128 caractères `[A-Za-z0-9._:-]`, sinon ignoré) : même patient et même clé dans les 24 h donnent la même alerte, réponse 201 rejouée depuis `Urgence.bilanDiffusion`, sans nouvelle diffusion ni 409. Stockage en base (unicité `patientId` + `cleIdempotence`), indépendant de Redis ; `cleIdempotence` et `bilanDiffusion` ne sortent jamais dans les réponses ; aucune coordonnée dans les journaux.
- **Ventes en pharmacie (B13, lot 7 ; B14, lot 8)** : module `src/pharmacie/` (`VenteController`, `VenteService`, DTO `dto/vente.dto.ts`). Quatre routes sous `/pharmacie`, gardes `AuthGuard` + `PermissionsGuard`, accès contrôlé par `AccesPharmacieService` (`src/pharmacie/acces-pharmacie.service.ts`, commun au stock et aux ventes) : membre de la pharmacie ou son administrateur quel que soit l'enum `role`, structure de type PHARMACIE (403 « Vous n'avez pas accès à cette pharmacie. » sinon) et active (403 « Cette pharmacie est désactivée. Contactez l’administrateur de la plateforme. ») : `POST /pharmacie/:structureId/ventes` (`vente:write`, 201), `GET /pharmacie/:structureId/ventes` (`vente:read`, 200), `GET /pharmacie/:structureId/ventes/:venteId` (`vente:read`, 200, 404 « Cette vente est introuvable. »), `POST /pharmacie/:structureId/ventes/:venteId/annuler` (`vente:annuler`, 200). Toutes les réponses sont `{ data, message, success }`.
  - Création : contrat de création remplacé par la tranche pharmacie 1 (PB11, puce « Vente recâblée » plus bas) ; liste et annulation remplacées par PB12 (puce « Annulation par pièce inverse » plus bas) ; les règles ci-dessous restent vraies pour le reste. Corps `{ lignes: [{ stockId, quantite }], clientNom?, clientTelephone?, ordonnanceVerifiee? }` avec, dans `champs[].contraintes` en cas de refus : `lignes` tableau (`isArray`) de 1 à 50 éléments (`arrayMinSize`, `arrayMaxSize`), `stockId` chaîne non vide (`isString`, `isNotEmpty`), `quantite` entier (`isInt`) de 1 (`min`) à 10000 (`max`), `clientNom` chaîne (`isString`) de 100 caractères au plus (`maxLength`), `clientTelephone` chaîne de 30 au plus (`maxLength`), `ordonnanceVerifiee` booléen (`isBoolean`). Une même ligne de stock ne peut apparaître qu'une fois (400 `VALIDATION`, champ `lignes`, contrainte `stockUnique`). En-tête facultatif `Idempotency-Key` (même règle que le SOS : 8 à 128 caractères `[A-Za-z0-9._:-]`, sinon ignoré) : même clé et même pharmacie dans les 24 h renvoient la même vente en 201, avec `data.rejeu: true` et le message « Cette vente était déjà enregistrée. », sans second retrait du stock ; unicité en base (`structureId` + `cleIdempotence`), un rejeu simultané est résolu par le conflit d'unicité. La clé n'est jamais renvoyée.
  - Forme renvoyée à la création, au rejeu, au détail et à l'annulation : `{ id, numero, statut, createdAt, total, ordonnanceVerifiee, clientNom, clientTelephone, vendeur: { id, nom }, annuleeLe, annuleeParId, motifAnnulation, lignes: [{ id, stockId, medicamentId, nomMedicament, prixUnitaire, quantite, sousTotal }], pharmacie: { id, nom, adresse, ville, telephone, logoUrl } }`. `data.rejeu: true` n'est présent QUE sur un rejeu (absent sinon). `statut` vaut `VALIDEE` ou `ANNULEE` ; `annuleeLe`, `annuleeParId` et `motifAnnulation` sont `null` tant que la vente est `VALIDEE` ; `clientNom`, `clientTelephone` et les champs de `pharmacie` absents valent `null` ; `logoUrl` est l'URL publique pérenne du logo de la structure (bucket public, `R2_PUBLIC_URL`) ou `null` sans logo, et `pharmacie` figure à la création, au rejeu, au détail et à l'annulation. Les noms et prix des lignes sont des copies figées au moment de la vente.
  - Liste : `GET .../ventes?date=AAAA-MM-JJ&page=` (défaut : aujourd'hui, page 1) renvoie `data: { date, totalJour, nombre, page, parPage: 50, totalPages, ventes: [{ id, numero, createdAt, statut, total, nombreArticles, vendeur: { id, nom }, clientNom }] }`, du plus récent au plus ancien ; `totalJour` ne compte que les ventes `VALIDEE`, `nombre` compte toutes les ventes du jour. Format de `date` hors `AAAA-MM-JJ` : 400 `VALIDATION`, champ `date`, contrainte `matches` ; date inexistante (ex. `2026-02-31`) : 400 `VALIDATION`, champ `date`, contrainte `dateValide` ; `page` entier (`isInt`) de 1 au moins (`min`). Messages de succès : liste `N vente(s) le AAAA-MM-JJ.`, création `Vente enregistrée (V-AAAA-NNNNNN).`, rejeu `Cette vente était déjà enregistrée.`, détail `Vente trouvée.`.
  - Annulation : corps `{ motif }` chaîne (`isString`) de 3 à 300 caractères (`length`, espaces retirés). Messages de succès : `Vente V-AAAA-NNNNNN annulée. Les quantités ont été remises en stock.` ; variante avec une ligne de stock supprimée : `Vente V-AAAA-NNNNNN annulée. 1 médicament n'était plus dans le stock et n'y a pas été remis.` (au pluriel : `N médicaments n'étaient plus dans le stock et n'y ont pas été remis.`). Seulement une vente `VALIDEE` du jour de sa création (jour UTC, Conakry est à UTC+0), permission `vente:annuler` (administrateur de la pharmacie, pas le pharmacien). Remet les quantités en stock par incrément atomique et remet `disponible` à vrai ; une ligne de stock supprimée depuis n'est pas remise, l'annulation réussit et le message le signale. Audit `annuler` sans le motif ni le client.
  - Erreurs sans code : 404 « Cette pharmacie est introuvable. » et 404 « Cette vente est introuvable. ». 403 `PERMISSION_REFUSEE` (code ajouté par le filtre à toute 403 sans code) : permission manquante (« Vous n'avez pas la permission d'effectuer cette action. »), pharmacie d'un autre utilisateur ou structure qui n'est pas une pharmacie (« Vous n'avez pas accès à cette pharmacie. »). Sans `details` : les 403 et les codes `VALIDATION`, `VENTE_DEJA_ANNULEE`, `ANNULATION_HORS_DELAI` (ces derniers portent `champs` pour `VALIDATION`). Plafonds : 1 à 50 lignes par vente, `details` tronqué à 50 éléments, `parPage` 50.
  - Erreurs avec `code` du catalogue `codes-erreur.ts`. Les codes à lignes (`STOCK_INTROUVABLE`, `MEDICAMENT_EXPIRE`, `PRIX_MANQUANT`, `ORDONNANCE_NON_CONFIRMEE`, `STOCK_INSUFFISANT`) portent `details`, assaini par `AllExceptionsFilter` (`CODES_AVEC_DETAILS`, 50 éléments au plus, seulement `stockId`, `nom`, `disponible`, `demande` du bon type) : 404 `STOCK_INTROUVABLE` (`[{ stockId }]`), 400 `MEDICAMENT_EXPIRE` (`[{ stockId, nom }]`), 400 `PRIX_MANQUANT` (`[{ stockId, nom }]`), 400 `ORDONNANCE_NON_CONFIRMEE` (`[{ stockId, nom }]`), 409 `STOCK_INSUFFISANT` (`[{ stockId, nom, disponible, demande }]`), 400 `VALIDATION` (corps invalide, doublon de `stockId`, total au-delà de 2147483647 avec la contrainte `totalMaximal`), 409 `VENTE_DEJA_ANNULEE` (testé avant le délai), 409 `ANNULATION_HORS_DELAI`. Ordre des refus à la création : ligne introuvable, puis périmé, puis sans prix, puis ordonnance non confirmée, puis stock insuffisant ; un seul code par réponse, avec toutes les lignes concernées. Tout refus annule toute la transaction (aucun retrait, aucun numéro consommé).
  - Règles : le prix vient du stock (jamais du client), un prix `null` ou 0 vaut « manquant » ; un médicament est périmé si sa `dateExpiration` tombe avant le jour courant à Conakry (UTC+0), le jour même reste vendable ; la vente retire la quantité seule (pas de remise ni de prix modifié) ; `disponible` passe à faux quand la quantité tombe à 0 ; l'alerte de stock bas (`STOCK_ALERTE`) part au franchissement du seuil de 10, sans jamais faire échouer la vente ; audit `create` de la vente. Numérotation `V-AAAA-NNNNNN` (`CompteurVente` par pharmacie et par année, incrémenté dans la transaction, qui verrouille la ligne et sérialise les ventes d'une pharmacie). Les retraits sont des décréments conditionnels (`quantite >= demandée`), jamais lire puis écrire. Une vente n'est jamais supprimée, seulement annulée ; `vendeurId`, `annuleeParId` et les identifiants des lignes n'ont pas de clé étrangère.
  - Prix du stock désormais entier (GNF, colonne `Int`, migration `20261022120000_ventes_pharmacie` avec arrondi) : `UpsertStockDto.prixUnitaire` en `@IsInt` (0 à 2147483647), import Excel arrondi à l'entier (rejet au-delà de 2147483647) ; `UpdateStockQuantiteDto.variation` en `@IsInt`. `updateStockQuantite` verrouille la ligne (`SELECT ... FOR UPDATE`) : plus de mise à jour perdue. Permissions des pharmacies : rôle « Pharmacien » : `stock:read`, `stock:write`, `vente:read`, `vente:write`, `caisse:utiliser` ; rôle « Administrateur de structure » : `stock:read`, `stock:write`, `vente:read`, `vente:write`, `vente:annuler` et les sept permissions de la tranche pharmacie 1 (plus `structure:*`, `membre:*`, `role:manage`). Rôles existants : `vente:*` repris par la migration du lot 7 ; depuis B14, `RolesService.completerRolesAdminPharmacie` ajoute au démarrage les 12 permissions de `PERMISSIONS_GARANTIES_ADMIN_PHARMACIE` au rôle « Administrateur de structure » de chaque pharmacie (ajout seul, invalidation du cache du rôle ; une de ces permissions retirée à la main revient au démarrage suivant). Hôpitaux et cliniques : ni `stock:*` ni `vente:*` (voir B10), cache `perms:v3`.
- **Imports Excel de la pharmacie (stock et catalogue)** : `src/pharmacie/import-excel.ts`. La ligne des titres est la première des 10 premières lignes qui contient toutes les colonnes obligatoires (stock : Médicament, Quantité ; catalogue : Nom, Catégorie), sinon 400 qui nomme les colonnes manquantes. Titres comparés en minuscules sans accents ni ponctuation (`normaliserTitre`), synonymes dans `reconnaitre` de `COLONNES_IMPORT_STOCK` (`pharmacie.service.ts`) et `COLONNES_IMPORT_CATALOGUE` (`catalogue-import.service.ts`) : Désignation, Produit, Libellé, Qté, P.U., Péremption, DCI, Famille… ; un titre de seuil (« Quantité minimale », « Stock alerte ») n'est jamais pris pour la quantité. - **Inventaire par lot (tranche pharmacie 1, PB15b)** : `POST` et `GET /pharmacie/:structureId/inventaires` et `GET .../inventaires/:inventaireId` (`inventaire:write`) ; comptage absolu par lot, en unités ou en boîtes du lot et unités en plus ; ciblage du lot par identifiant, numéro, date (lot épuisé compris) ou lot unique de la fiche, même épuisé ou négatif (D600) (sinon 409 `LOT_REQUIS` avec les lots, ou nouveau lot daté) ; un mouvement `INVENTAIRE` par lot compté, même à écart nul ; tolérance par fiche (somme des écarts des lots), anomalie `ECART_INVENTAIRE` attribuée à l'auteur au-delà ; les ventes faites sans stock sont rattachées aux lots comptés, qui finissent à la quantité comptée ; le théorique est lu à l'enregistrement (une vente entre le comptage et la saisie compte comme un écart) ; verrous comme la réception ; cœur `enregistrerDansTransaction` (mode `rejeterLignes`) et `simuler` réutilisables par l'import.
- **Import Excel d'un inventaire (tranche pharmacie 1, PB15c)** : mode `inventaire` (défaut, `inventaire:write`, 403 sinon) enregistré comme un inventaire par lot de PB15b (commentaire « Import Excel ») ; quantité comptée en boîtes (0 permis) et unités en plus ; une ligne par lot, lot trouvé par numéro ou par date ; plusieurs lots sans précision : ligne rejetée avec la liste des lots ; boîtes d'un lot inconnu : nouveau lot (date obligatoire, date passée acceptée) ; médicament absent : fiche créée si la quantité est positive ; prix, coût et notes ignorés ; lignes refusées rejetées une par une ; réponse `inventaireId` ; modèle `GET .../import/modele?mode=inventaire`.
- **Alertes de péremption et marge (tranche pharmacie 1, PB16a)** : `GET /pharmacie/:structureId/stock/alertes-peremption` (`stock:read`) classe chaque lot en stock dans le plus petit horizon des paramètres (défaut 90, 30, 7 jours), périmés à part, lots sans date comptés ; valeur au prix de la boîte pour tous, valeur au coût seulement avec `marge:read` (masquerCouts), un coût inconnu n'est jamais compté pour 0. `GET /pharmacie/:structureId/rapports/marge?du=&au=` (`marge:read`, 92 jours au plus) réutilise `calculerMarge` : un lot à coût 0 (reprise, trouvé à l'inventaire, reçu sans coût) rend la vente non valorisable, provisoires à part, `debutFiabilite` affiché (D602 à D605).
- **Étanchéité des coûts (tranche pharmacie 1, PB16b, CA22)** : `test/etancheite-couts/routes-pharmacie.ts` inventorie toutes les routes `/pharmacie` ; `src/pharmacie/etancheite-couts.spec.ts` échoue si une route exposée manque à l'inventaire (découverte par la métadonnée Nest depuis `AppModule`) ou si un fichier hors `src/pharmacie/` lit un coût ; `test/db/etancheite-couts.db-spec.ts` appelle chaque route avec un vendeur qui a toutes les permissions de pharmacie sauf `marge:read` et échoue sur toute clé `/cout|marge/i`. Une nouvelle route : l'ajouter à l'inventaire et à `APPELS`, et masquer ses coûts par `masquerCouts`. Les paramètres de la pharmacie ne renvoient plus `debutFiabiliteMarge` (exposé par le rapport de marge, D610).
- **Clôture journalière (tranche pharmacie 1, PB17a)** : `GET /pharmacie/:structureId/caisse/clotures/:jour/preparation`, `POST /pharmacie/:structureId/caisse/clotures` (`{ jour, forcer?, motifForcage? }`, 200) et `GET .../caisse/clotures?mois=AAAA-MM` (`cloture:gerer`). Jours clôturables de `debutCaisse` à aujourd'hui, dans n'importe quel ordre, journée vide comprise (400 `JOUR_AVANT_DEBUT_CAISSE`, 400 `VALIDATION` `jourFutur`). Forcer exige un motif (400 `MOTIF_REQUIS`) et n'est permis que si tous les postes attendus sont desktop : une caisse ouverte sur un navigateur se ferme avec le comptage (409 `CAISSES_A_FERMER`). La clôture passe les caisses fermées du jour en `INCLUSE_DANS_CLOTURE`, fige `TotalClotureMode` (compté nul si une caisse n'a pas de relevé pour un mode qu'elle a encaissé) et consigne les postes manquants (`posteId`, `posteCode`, `libelle`, `type`, `raison`, `sessionId`, `utilisateurNom`, `dernierContactLe`) ; une caisse desktop ouverte reste ouverte. 409 `JOURNEE_DEJA_CLOTUREE`. Verrou consultatif de journée `medconnecte:journees:<structureId>` pris en exclusif en tête de la clôture (`src/pharmacie/caisse/journee.ts`, D613). Export : `GET .../caisse/clotures/:jour/export` (`cloture:gerer`, journée clôturée seulement, sinon 409 `JOURNEE_NON_CLOTUREE`) renvoie un CSV `cloture-AAAA-MM-JJ.csv` (point-virgule, UTF-8 avec BOM) : une ligne par pièce (vente, annulation, régularisation), par paiement (montant signé, référence) et par mouvement de caisse (apport positif, prélèvement et remboursement négatifs), colonne « Caisse incluse dans la clôture », sans coût, sans client, sans médicament ; formules Excel neutralisées, référence de paiement faite uniquement de chiffres précédée d'une apostrophe (D622, D628).
- **Journée clôturée (tranche pharmacie 1, PB17c)** : vente, annulation, ouverture de caisse, comptage, mouvement de caisse et fermeture prennent en tête de transaction le verrou de journée partagé (`verrouillerJourneesPartage`), la clôture le prend en exclusif : aucune écriture ne s'intercale. Ordre des verrous : journées, poste, session, compteur de tickets ou vente d'origine, fiches. Une caisse dont le jour métier est clôturé (caisse desktop restée ouverte après une clôture forcée) refuse toute écriture : 409 `JOURNEE_CLOTUREE`. Une caisse ouverte après la clôture du jour compte pour le lendemain (`jourMetierOrigine` = jour réel) : aucune vente n'est refusée pour ce motif. Une correction se fait par écriture inverse rattachée à la journée en cours qui pointe l'origine (annulation, CA20). Une réception datée d'un jour antérieur clôturé est refusée ; le journal de stock (inventaire, sortie, corrections, résolution des provisoires) est horodaté au présent et n'est jamais refusé (D614). Tout nouvel écrivain de caisse (rejeu PB18 compris) s'ajoute au test 11 de `test/db/journee-cloturee.db-spec.ts`, qui exige qu'il attende une clôture en cours avant sa première lecture (D629).
- **Synchronisation desktop (tranche pharmacie 1, PB18)** : `POST /pharmacie/:structureId/postes/:posteId/plages` (`caisse:utiliser`, 200, `{ id }` UUID du poste) réserve `taillePlageTickets` numéros sur `CompteurTicket` pour un poste DESKTOP actif (idempotent par `id`, 409 `IDENTIFIANT_DEJA_UTILISE` pour l'id d'un autre poste, 409 `PLAGES_SUFFISANTES` au-delà de deux plages non épuisées, 409 `POSTE_INCONNU` pour un poste web, technique, inactif ou inconnu) ; une plage est épuisée quand son dernier numéro ou un numéro d'une plage plus récente du poste est utilisé ; la réponse liste les plages en cours. `GET /pharmacie/:structureId/synchro/catalogue?posteId=` (`caisse:utiliser`) renvoie la photographie complète du catalogue pour un poste desktop actif (fiches non archivées, lots à solde positif périmés compris, paramètres, modes, coupures, pharmacie, plages en cours, `sequenceAppliquee` et `sequenceMaxRecue`), sans aucun coût même pour le titulaire, lue en lecture répétable, avec ETag faible (304 si `If-None-Match` correspond) et compression brotli ou gzip selon `Accept-Encoding` (D633, D634) ; aucun champ qui dépend de l'heure dans la photographie, le poste lit l'heure du serveur dans l'en-tête `Date` (D662). CORS : `DESKTOP_ORIGINS` (D635), en-têtes exposés `ETag` et `Date`. `POST /pharmacie/:structureId/synchro/evenements` (`caisse:utiliser`, 200, corps JSON jusqu'à 2 Mo, gzip accepté ; seule route ainsi : partout ailleurs 100 Ko et 415 sur un corps compressé, `monterAnalyseursJson` de `src/config/analyseurs-corps.ts`, à monter avant `init`, D663) : `{ posteId, etat: { fileVide, sessionOuverte, versionApp }, evenements: [{ evenementId, sequence, type, horodatageLocal, utilisateurId, corps }] }` (0 à 200 ; lot vide = battement de cœur). Une transaction par événement, verrou de journée partagé en tête puis poste ; idempotent par `evenementId` et empreinte ; ordre strict par poste (`EN_ATTENTE` puis application dès que le trou est comblé, saut après 24 h avec `SEQUENCE_MANQUANTE`) ; statuts `APPLIQUE`, `DEJA_APPLIQUE`, `EN_ATTENTE`, `REJETE` (stocké avec son corps, séquence avancée, anomalie `EVENEMENT_REJETE` sans donnée du client), `A_RENVOYER` (rien d'écrit, renvoyer plus tard ; au 3e échec imprévu du même événement, hors panne passagère de la base, il est mis de côté `REJETE` `EVENEMENT_INAPPLICABLE`, compteur dans `Poste.dernierEtat.echecImprevu` ; un caractère NUL donne `EVENEMENT_INVALIDE` et le corps est stocké en texte `{ corpsIllisible }`, D664) ; réponse `{ resultats, sequenceAppliquee, enAttente }`, avec les événements en attente traités pendant l'appel (`differe`). Le vendeur d'un événement doit être de la pharmacie (`UTILISATEUR_NON_AUTORISE`). Écrit `Poste.dernierContactLe` et `dernierEtat` (`fileVide` = déclaré et rien en attente). Événements de caisse : `SESSION_OUVERTE` (jour local, ou jour de rattachement si clôturé), `COMPTAGE_SAISI`, `MOUVEMENT_CAISSE` (appliqués sur une caisse ouverte même d'un jour clôturé), `SESSION_FERMEE` (jamais refusée ; caisse d'un jour clôturé : FERMEE, jamais incluse, anomalie `REMONTEE_APRES_CLOTURE` au titulaire). Le cœur de fermeture est `SessionsCaisseService.fermerSessionVerrouillee` (D650). Le rejeu figure au test 11 de `journee-cloturee.db-spec.ts`.

## Mode démo (`src/demo/`)

Actif seulement si `DEMO_MODE=true` (avertissement au démarrage, renforcé en production).
`DemoSeeder` crée au boot, une seule fois et dans une transaction, un jeu de données
guinéen fictif (5 structures, 20 comptes, carnets chiffrés via `EncryptionService`,
stocks, messagerie, SOS, notifications), puis rattache les rôles RBAC. Le compte vitrine
patient (Aminata Diallo) porte un dossier riche sur 3 ans (9 consultations dans 3
structures, ordonnances sans pénicilline car elle y est allergique, analyses, vaccins,
rendez-vous, messagerie). Comme le seed ne crée rien si des données démo existent déjà,
`DEMO_RESET=true` (avec `DEMO_MODE=true`) supprime au démarrage toutes les données démo
(comptes et structures en `@demo.medconnecte.gn`, leurs journaux d'audit, et tout ce qui
leur est rattaché par cascade) puis recrée le jeu complet, dans une seule transaction ;
le catalogue de médicaments, partagé, n'est jamais supprimé. Purge physique volontaire
(pas de soft-delete sur ces données fictives), journalisée « Données de démonstration
supprimées puis recréées ». À remettre à `false` ensuite, sinon chaque redémarrage
recrée les données (nouveaux identifiants, sessions démo invalidées). `DEMO_RESET=true`
sans mode démo : avertissement, rien n'est supprimé. Un compte démo
se reconnaît à son email en `@demo.medconnecte.gn` ; son mot de passe est aléatoire et
inconnu, et son mot de passe comme son email ne peuvent pas être modifiés. Aucun email ni SMS réel ne part depuis ou vers un compte démo : `EmailService` ignore toute adresse en `@demo.medconnecte.gn`, le SOS d'un patient démo ne prévient pas son proche (le patient en est informé), et l'OTP de partage d'un patient démo n'envoie pas de SMS mais renvoie le code à l'accueil (`codeDemo`, seulement si le mode démo est actif). Routes
publiques : `GET /auth/demo/comptes` et `POST /auth/demo/connexion` (`{ userId }`, même
réponse et même cookie que `POST /auth/login`, 403 pour tout compte non démo). `GET /auth/demo/comptes`
propose un compte par rôle, et deux administrateurs de structure (Hôpital National Donka,
Pharmacie de Kaloum : stock, ventes et annulation). Mode
inactif : 404 sur ces deux routes et aucune donnée créée. Ne jamais activer sur une
instance qui contient de vraies données de santé.
